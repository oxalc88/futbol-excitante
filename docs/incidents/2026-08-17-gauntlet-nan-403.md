# NaN/DeepSeek HTTP 403 API incident

## Summary

On 2026-08-17, two consecutive NaN Chat Completions calls returned the following text:

```text
HTTP 403: System error, please try again later.
```

Both responses were persisted as assistant messages from `deepseek-v4-flash`. The client streamed each response and marked each turn completed instead of recording a terminal inference failure.

The raw HTTP response headers and JSON body were not persisted. Consequently, the provider request ID, raw error message, and NaN error `code` cannot be recovered from the client artifacts.

Follow-up API probes using the same running-process credential succeeded. This rules out a persistent missing-key, invalid-model, or endpoint-configuration problem and is consistent with a transient provider-side access-control or tier-gate failure.

The 18 assistant records contain 40 tool calls. The client prepared 26 tool definitions for the turn. Their final serialized representation was not captured.

The actual message contents are intentionally excluded because they are not needed to correlate an authorization failure and may contain private source context. The client may also transform messages or attach request parameters and tool schemas during serialization.

## Captured API evidence

- Exact selected model and Chat Completions backend.
- Configured API base URL.
- Presence of the configured environment credential.
- Session ID, client version, timestamps, event IDs, and prompt IDs.
- Persisted conversation records supplied to the client request builder.
- Exact assistant text produced for both failures.
- Streaming lifecycle showing both responses were marked completed.

## Missing API evidence

- Byte-for-byte serialized request JSON.
- HTTP request headers.
- Provider request ID, Cloudflare ray ID, or upstream trace ID.
- Raw HTTP status line, response headers, or JSON error object.
- NaN error `code`, such as `tier_restricted`.
- Provider-side routing target or worker identity.

No `shell.turn.inference_failed` record exists for these calls. Other API failures recorded by the same client include an HTTP status and a `sampler_request_id`; their absence here indicates that the custom-model adapter surfaced this error through the normal assistant-message stream.

## Credential and documented error behavior

- `NAN_API_KEY` was present and non-empty in the running client process.
- The credential value and fingerprint are intentionally excluded.
- The same model successfully completed earlier calls in the session.
- NaN's API documentation classifies HTTP 403 as a tier access denial (`tier_restricted`). It documents HTTP 429 for rate or quota exhaustion: <https://nan.builders/docs/api>.

Because the raw response was not recorded, `tier_restricted` is an inference from the documented HTTP status, not an observed provider error code.
