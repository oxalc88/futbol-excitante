# Gauntlet 0.11.3 — shared recovery budgets and stop rule

Patch over 0.11.2. Repair verification could still repeat an expensive whole-suite check indefinitely, especially when worker errors did not identify failing test files. The fixed 20-minute command limit also conflicted with the worker's reported 26–32-minute Node battery on a contended 2-vCPU host. Those timings are worker-reported evidence, not measurements reproduced for this release.

The canonical whole Node regression check gets 40 minutes; other checks retain 20 minutes. Focused Node repairs retain 20 minutes. Each executed row records its actual timeout. The optional verification-batch wrapper recognizes the exact canonical quality command and allows the maximum protected plan, or one repair check, plus 30 seconds for setup/cleanup. The inner runner still enforces every timeout and the recovery deadline. Other batched commands retain their original budget; no arbitrary timeout parameter is added.

Recovery has two repair attempts and a 90-minute elapsed deadline per objective, including diagnosis, idle time and the subsequent full gate. Attempts are reserved atomically before launching repairs and remain consumed after interruption or success. Changing sources, failure signatures or sessions does not reset the budget. The last passing allowed repair can unlock its one fresh full gate within the deadline. Exhaustion without a current proof, expired deadlines and clock rollback produce RECOVERY_BLOCKED, a non-accepting receipt and a local blocked report with failure/budget/log references. A full PASS ends recovery. Old 0.11.2 records receive prospective budgets with earlier recovery history explicitly UNAVAILABLE; no missing history becomes measured zero.

OMP, Grok and OpenCode automatically consume the same shared instruction: stop equivalent experiments when blocked, preserve the candidate and logs, report the next decision and keep dependencies blocked. Smaller reproductions must establish the cause before repair verification. Raw harness tools remain available; the shared instruction prohibits bypassing the canonical runner, but it is not an OS-level shell sandbox. Independent ready product work may continue under the existing dependency rules. Resumption after exhaustion requires a reviewed environment or execution-policy decision, not an automatic reset or retry.

All required tests/checks, affected-domain assurance, independent review, evidence, provenance and acceptance gates remain intact. Passing assertions do not waive unhandled worker errors or failed process exits. Existing CI main/head regression classification does not waive candidate acceptance. No application source, capture launcher, Vitest configuration, dependency or accepted historical state/evidence is changed. This release does not claim to fix the reported Vitest RPC error or improve product throughput.

## Validation

Seven new Gauntlet tests cover the scoped Node/wrapper budgets, deadline clipping/clock rollback, attempt retention across changed signatures/sources, prospective old-record history, blocked receipt rejection, and command-level multi-session refusal before another test launches. Existing 0.11.2 coverage retains fail-fast, stale-proof, whole-check escalation, fresh-full acceptance and poisoned-command rejection; its integration flow now fits the two-repair limit. Product tests pass 54/54 and 0.10 runtime tests pass 8/8. Gauntlet maintenance validation also covers deterministic scenarios/prompt gates, state audit, parallel/telemetry/selector policy, architecture/candidate tests, typecheck, build and worktree hygiene. Chromium is not required for this Gauntlet-only patch. Historical accepted-evidence mismatches remain visible under the unchanged CI classifier; no manifest is edited to make them green. The affected server worker and full application suites were not executed here.
