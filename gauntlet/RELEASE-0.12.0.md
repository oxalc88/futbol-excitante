# Gauntlet 0.12.0

Separates objective acceptance from repository certification so valid product progress does not depend on repeatedly regenerating an unrelated whole-repository receipt. This implements the acceptance-boundary investigation in design PR #32. The release becomes active on main after merge; existing running sessions must reload canonical instructions.

## Changed behavior

- Objective verification selects contract/architecture regression baseline, real affected imports and existing protected-domain checks from both source trees. Unmapped/dynamic, deterministic core, replay/persistence, shared configuration or elevated-risk scope requires complete verification immediately. Existing independent critic/integration applicability remains enforced.
- Repository certification runs complete Node/browser inventories, smoke, typecheck/build, contracts/state, parallel policy and telemetry at milestone/release, explicit-request and bounded integration boundaries. The exact frozen target must have a full PASS before milestone evaluation; playtest evidence names that target.
- Durable objective acceptance uses schema 4 with objective proof scope and `repository_certified: false`. A supported unrelated harness certification failure can permit already-selected same-Horizon work through its own required checks, up to four uncertified objectives. Product, unknown or invalid certification failures cannot authorize scoped continuation. Intervening unaccepted source changes force certification.
- Immutable per-check proof JSON binds input content/inventory, command, verifier protocol, pinned toolchain and hashed environment, with compressed full logs/original test reports. Only matching complete PASS evidence is reusable. Whole-check repair can cover the same check once; focused repair cannot cover a broader check. State audit stays fresh. No failed run is relabeled PASS.
- Certification records are append-only, target-bound and published separately from candidate snapshots. Existing acceptance provenance, manifest/durability, evidence classes, qualitative playtests and serialized state publication remain required.
- All OMP/Grok/OpenCode launch and continuation entrypoints consume the canonical policy. Model routes, native scheduling/retries, telemetry, memory/context, checkpoints, rotation and issue-gated parallel work remain unchanged.

## Recovery and migration

Keep the 0.11.3 policy unchanged: whole Node 40 minutes, other/focused checks 20 minutes, two repair attempts and a 90-minute incident deadline. Certification uses one worktree/repository incident so changing a CERT label cannot reset recovery. Objectives have separate incidents. Old broad records remain unchanged diagnostics and grant no new-scope PASS. Certification imports unresolved legacy incidents with the earliest deadline/greatest attempt count and source hashes, preserving the original files. A required full scope still honors an old exhausted incident; bounded affected work does not inherit an unrelated broad certification failure. An exhausted incident still requires a reviewed environment/execution-policy decision; this release does not grant a budget reset.

Existing accepted records/state/releases are not migrated or rewritten. A first scoped acceptance requires a newly recorded certification attempt, followed by separate remotely verified publication. Bootstrap may permit bounded same-Horizon continuation only if the failure cause is supported harness evidence. Capture-test repairs or application/Vitest configuration changes on a running worker remain separate work; this PR changes Gauntlet only.

Canonical objective command: `mise exec -- pnpm run gauntlet:quality -- --base <candidate-parent> --execute --out docs/evidence/<objective>/quality.json`.

Canonical certification command: `mise exec -- pnpm run gauntlet:quality -- --stage certification --target HEAD --execute --out docs/evidence/CERT-<boundary>/quality.json` with committed inputs. Publish certificate records/proofs through git-committer, then push and verify remote containment. Candidate snapshots cannot contain certificate bookkeeping. At an eligible blocked certificate, proceed through the already-selected objective's required checks/reviews/acceptance/publication; no custom prompt or PASS override is needed.
