# Product-first autonomous execution — 0.13.0

VISION governs product outcomes. A product issue can own several temporary execution units, but gets one integrated candidate and one acceptance. Play the normal shipped app, compare it with the before-evidence, and iterate autonomously until it is materially better. Objective verification, independent reviews, evidence, provenance, persistence, state audit and remote durability remain mandatory. Full certification is the separate integration/four-objective, milestone and release boundary described in `product-quality-contract.md`.

## Deterministic continuation

`runtime/continuation.ts` is the single continuation policy. All harnesses run `mise exec -- pnpm run gauntlet:control -- continue` before returning control. At upgrade, publish the canonical legacy-import manifest/events before starting a candidate; this is routine bookkeeping, and must precede candidate scope. With a blocker, pass `--facts <file>` containing the preserved progress, attempted autonomous actions and observed external-capability availability. The command recomputes same-Horizon admission from canonical state; a local packet cannot assert that work is safe.

Select executable current-Horizon work; decompose implementation; compute actual impact; reuse valid proofs; perform required reviews; repair routine bookkeeping; publish acceptance; continue. Completion, a certificate failure, an expired incident, a failed unit or a routine deterministic choice cannot stop the loop. If no safe work is yet proven and no external decision exists, diagnose or replan automatically. A replan must preserve certification debt and cannot create a fresh Horizon to evade a blocked certificate. Infrastructure cannot recursively generate infrastructure objectives.

Before stopping, determine the blocked boundary and cause, preserved progress and debt, every same-Horizon work item considered, applicable deterministic actions, bounded repair history, applicable external engineering escalation, and the exact remaining external decision. External decisions are specification, legal, unavailable perceptual route, inaccessible credentials/resources, environment/execution policy after bounded repair and applicable engineering escalation, or an explicitly defined external decision. A quota handoff preserves work for the next native harness session; it is not a product-policy stop. Exhausted builders are decomposed/rerouted or blocked while safe work continues.

`gauntlet:control -- stop --facts <file>` refuses a stop without an exact external decision or while safe canonical work exists. It appends `gauntlet/incidents/stop-<hash>.json`: stop_reason, incident_id, blocked_boundary, failure_class, preserved_progress, certification_debt, safe_work_considered, autonomous_actions_attempted, evidence, exact_decision_required and source commit. Publish this record through the existing serialized committer and verify remote containment. Report its path and decision in the harness. Free-form worker questions are not the stop mechanism.

## Current simulation boundaries

Scope is calculated from Git snapshots and actual transitive test imports. No model classifies it.

| Boundary | Objective verification |
|---|---|
| Ball, locomotion, contact/player-contact systems and foul/card/advantage policies | Body-only edits with unchanged imports/global/public surfaces use baseline, transitive affected tests, protected-domain inventories, simulation/browser checks and independent reviews |
| Loop restart/foul/serve helper bodies in the closed AST allowlist | Same affected verification; imports, signatures, step/update skeleton and public declarations must remain identical |
| Input slot/player selection helper bodies in the closed AST allowlist | Same affected verification; scheduler memory, duplicate handling, input fallback, public types/signatures and wiring assurance remain outside this boundary |
| Clock/update order, RNG/canonical state, world create/clone/validation, replay/persistence, shared configuration/contracts, assurance/evaluator integrity, elevated risk, new/unresolved/dynamic impact | Full verification |

The helper classifier refuses new calls, computed accesses or mutation targets and protected machinery/I/O changes. Unknown changes stay full. Unit handoff/local-check artifacts are validated separately and do not turn a mapped product edit into broad source impact. Integrated candidates always require both independent reviews.

## Canonical incidents and bounded machinery work

`gauntlet/incidents/<incident-id>/<sequence>.json` is the only incident ledger. Events are append-only, hash-linked and validated by the runner and state audit. Original failure proof, attempts, budget start/deadline, evidence and provenance survive every transition. Existing .delivery-local recovery files are imported once, byte-for-byte, with a canonical migration manifest; they then have no policy authority. Import preserves the earliest deadline and greatest measured attempts at a shared full boundary. Unrecorded earlier history remains UNAVAILABLE. Import errors fail closed.

A full-required objective and certification share the repository/full incident boundary. A mapped objective uses its own boundary and does not inherit unrelated certification recovery. Objective/session/model/CERT/process labels do not change incident identity. Local caches, locks, telemetry, diagnoses, escalation packets and runtime credentials have no independent policy authority. Do not track .delivery-local as a whole.

Lifecycle: ACTIVE → EXHAUSTED → REPAIR_CONFIRMED → RESUME_ONCE → CLOSED on complete verification PASS, or BLOCKED on failure/interruption. A repair may also be confirmed while ACTIVE. Exactly one causal diagnosis, one machinery repair/reproducer and one reserved execution are permitted per incident. Failed diagnosis/repair or an interrupted consumed execution does not grant another experiment. Return to safely verifiable product work; when none exists, use the applicable external engineering escalation or record the exact external decision.

1. Publish the original incident and failure evidence.
2. Diagnose once. Commit a material repair confined to verification machinery. Do not change product code or requirements, assertions, tests, budgets, timeouts or retries to escape the stop.
3. Run the derived focused reproducer via `gauntlet:quality --repair <repair.json>` at the original boundary. The JSON contains diagnosis, component, and repair_commit. The repaired component must be an existing statically attributable original-check dependency or canonical execution transport; new unrelated executable code is rejected. Use one atomic machinery repair commit on the published original-incident baseline; intervening source changes cannot hide policy, assertion or budget changes in a parent commit. Canonical bookkeeping/evidence commits are allowed in that range. Broader source changes require ordinary verification. When the repair changes the calculated candidate scope, pass `--incident <original-id>` on repair and resumed execution. This binds the original incident without narrowing the recalculated verification plan. Gauntlet validates the changed machinery commit, exact derived command, zero exit, immutable log/report proof, coverage, toolchain/environment and input identity before appending REPAIR_CONFIRMED. REPAIR_PASS is diagnostic only, never objective acceptance or certification.
4. Publish the repair evidence. Run `gauntlet:control -- reserve-resume --incident <id>`. Publish the reservation and verify remote containment, then run the normal canonical quality command. These are routine autonomous committer actions, not human approvals.
5. The reservation grants one execution, not another normal recovery budget. It retains the original start, deadline and attempt history; check timeouts remain unchanged. A workspace-bound random execution credential is temporary transport, validated against the canonical reservation hash and consumed before launch. Another checkout without that credential cannot run the reserved execution. If interrupted after consumption, preserve BLOCKED and escalate; never reconstruct the credential or reserve twice.

For a resumed objective, publish the verified candidate, then run `gauntlet:control -- close-incident --incident <id> --candidate <sha> --objective <id>` before acceptance bookkeeping. Closure freezes the candidate identity; certification already freezes its target and closes directly. The runner consumes reservation state before running checks, reuses only fully validated equivalent PASS proofs, and appends CLOSED only after validating the complete required-plan receipt. No harness failure becomes PASS. Publication is serialized by the existing committer/worktree contract; the core adds no scheduler, wait controller, concurrency governor or backoff mechanism.

## External engineering transport

`gauntlet:control -- escalate --incident <id>` records one canonical escalation event and derives `.delivery-local/escalation/<id>.json`. Use any available authorized engineering agent; Codex is optional. The packet includes original incident/event, boundary, classification, exact failing check, log/proof references, prior diagnosis/repair, preserved progress, certification debt, environment/toolchain identity, permitted machinery scope, prohibited actions and recovery evidence requirements. It is transport only. Refresh it from canonical state before use.

The external agent can inspect Gauntlet, harness integration and verification tooling, diagnose and propose/commit a machinery repair, and run the one authorized diagnostic reproducer through Gauntlet. It cannot waive tests, rewrite FAIL, reset incidents, raise budgets, weaken assertions, alter requirements/product code or certify its own repair. Only the canonical runner can validate proof and append repair confirmation/reservation. Escalation after the one repair has failed is engineering review of the exhausted incident and environment decision; it grants no second machinery repair or recovery budget.

## Execution units and one acceptance

Persist a plan at `gauntlet/execution/<objective>.json` using `execution-plan.example.json`; replace its placeholder with the actual source commit. Its issue_number identifies the substantial product outcome. Units define purpose, dependencies, expected file ownership, builder role, known interfaces, local checks and handoff contract. Units do not have product acceptance records or separate product issues.

`gauntlet:control -- execution --objective <id>` validates the DAG and canonical unit results. Core determines dependencies, readiness, ownership conflicts and topological integration order only. Conflicts serialize in plan order. Unknown interfaces wait. If no useful parallelism exists, use one worker. The harness owns task invocation, isolated workspaces/worktrees and native task settlement, concurrency and retries.

Record a unit result once at `gauntlet/execution/<objective>/<unit>.json` with unit_id, base_commit, output_commit, handoff path/hash, local check proofs, and receipt_path. The plan base_commit is the product source commit before the plan publication. A worker base may add only that parent’s canonical plan/settlement metadata to the deterministic dependency integration. Write `docs/evidence/<parent>/units/<unit>/handoff.md` before checks, run `gauntlet:quality --objective <parent> --unit <unit> --execute`, and commit the output in its isolated workspace. In the coordinator, `gauntlet:control -- settle-unit --objective <parent> --unit <unit> --base <worker-base> --output <commit> --handoff <path>` derives and validates the settlement. Publish all settlements before constructing the candidate. Check proofs use the existing immutable check-proof format; handoff content is not acceptance. Core validates output ownership, dependency settlement, immutable handoff and exact local checks. Integrated candidates always receive independent critic and integration review, including presentation-only units. Integrate all unit commits in the reported order using the native Git/harness merge mechanics. For independent units, a native `git merge --no-commit --no-ff <ordered-outputs>` preserves the coordinator HEAD as candidate parent and the unit outputs as merge parents. Verify this pending integration with the coordinator HEAD as `--base`; the runner validates HEAD plus native MERGE_HEAD provenance before the committer creates the candidate with quality evidence. The final acceptance validator checks actual committed ancestry. Dependency integrations must contain every dependency output and the exact merged source tree; the full worker base-to-output history must stay within ownership. Integrated acceptance rejects incomplete units or output commits absent from the candidate ancestry. It then uses the existing candidate impact/check/review/evidence/provenance/persistence/state/remote pipeline once. A unit failure preserves completed unit outputs and leaves independent units executable.

Only after integrated product acceptance, normal shipped play and remote durability may the parent product issue close. Existing parallel-issues commands remain compatibility tooling for genuinely independent objectives; they are not required for units under one issue. The OMP gate accepts `[gauntlet-objective:<parent>] [gauntlet-unit:<unit>]` tasks using canonical DAG readiness. Grok/OpenCode use the same core command and their native execution tools.

## Notification capability, observed from adapters

Core guarantees canonical structured stop/escalation state, durable after the existing Git publication step. It cannot guarantee delivery to an absent user.

OMP already exposes ctx.ui.notify in the efficiency extension. The thin adapter displays the latest canonical stop on session_start/tool_result, once per loaded session; it contains no stop policy. Grok and OpenCode currently have textual command/session output, with no notification API in the committed adapters. Out-of-session push/mobile/email notification is unsupported by all current adapters. No capability is invented. Historical stop records remain visible as history; a resumed worker must state whether the cited stop still applies.
